# GS Map Editor の開発

*これは英語版 [DEVELOPING.md](../DEVELOPING.md) の翻訳です。内容が異なる場合は英語版が最新です。*

エディターの実行・ビルド・テスト・更新の方法と、各機能の内部の仕組みについて説明します。使い方を知りたい場合は [README](../../README.ja.md) を読んでください。

## ソースからの実行

Pillow 入りの Python 3 と、ビルド済みの alchemy チェックアウトが必要です。

```sh
python3 server.py                  # alchemy は ~/gs_project/alchemy-port
python3 server.py --root /path/to/alchemy --port 8765
# http://127.0.0.1:8765/ を開く
```

### デスクトップアプリ（macOS）

`GS Map Editor.app` は、エディターを独立したウィンドウで開くもので、ターミナルを一度も開かないプレイヤー向けです。

```sh
python3 -m venv .venv && .venv/bin/pip install pywebview pyinstaller pillow
python3 packaging/build_toolchain.py                          # GBA 用 binutils + libpng、約 10 分、初回のみ
.venv/bin/python packaging/make_icon.py                       # packaging/icon.icns
.venv/bin/pyinstaller --noconfirm packaging/gsmapedit.spec    # -> dist/GS Map Editor.app
python3 packaging/make_dmg.py                                 # -> dist/GS-Map-Editor-<version>.dmg
python3 packaging/sign_and_notarize.py --identity "Developer ID Application: …"   # Apple Developer アカウントが必要
.venv/bin/python desktop.py                                   # パッケージ化せずに実行することもできる
```

アプリは自前のビルドツール（`packaging/toolchain`、15 MB）を同梱しています。GBA 用の GNU binutils、静的リンクの libpng、そして alchemy の `tools/Makefile` に応答する小さな `libpng-config` の代用品です。これらは固定されチェックサムで検証されたソースからビルドされ、macOS 以外には何も必要としません。これがあるので、プレイヤーに必要なのは Apple の無料の開発者ツールだけです。Homebrew はツールチェーンを含まないビルドでのみ使われます。`GSMAP_NO_BREW=1` を指定すると Homebrew が見えなくなり、ビルドが Homebrew を必要としないことを確かめられます。

初回起動時にはセットアップのチェックリスト（`static/setup.html`、`gsmap/setup.py`）が表示されます。各ステップは推測ではなく必ず確認され、時間のかかるステップはログをリアルタイムで表示します。
1. Apple の開発者ツール（Apple のインストーラーを開きます）。
2. ビルドツール: アプリに同梱されています。同梱していないビルドでは Homebrew と alchemy の INSTALL.md にあるパッケージにフォールバックし、フォーミュラ名ではなくビルドが実際に使うものによって確認します。
3. ゲームのソース: alchemy（このエディターがテストされたコミットに固定）を `~/Documents/GSMapEditor/` にダウンロードする（スペースは不可: ビルドが扱えません）か、既存のチェックアウトを選びます。
4. `make bootstrap`（ゲームのコンパイラー。alchemy の `alchemy-gcc` サブモジュールにあるソースから一度だけビルドされ、ダウンロードはありません）、続いて最初の `make tbs-en`。

その後は、アプリを開くとそのままエディターが表示されます。設定は `~/Library/Application Support/GS Map Editor/` に保存されます。アプリはゲームデータを一切含みません。ゲームはプレイヤーの Mac 上で alchemy のソースからビルドされます。2 つのサーバーはどちらもこのマシン上だけで、ランダムなトークンの背後で待ち受けます。`desktop.py --no-window` はテスト用にそれらのアドレスを表示します。

### Linux と Windows（WSL）

Linux ではエディターはソースから実行され、ブラウザーで開きます。`python3 desktop.py`（`python3-pil` が必要）は同じセットアップのチェックリストを表示し、Homebrew の代わりに alchemy の INSTALL.md にある apt パッケージを使います。それらのインストールには `sudo` が必要なので、チェックリストはコマンドを実行せずに表示します。設定は `~/.config/gs-map-editor`、ビルドキャッシュは `~/.cache/gs-map-editor`、ゲームのソースと書き出したファイルは `~/GSMapEditor` に置かれます。システムによって異なる部分（フォルダー、リンクを開く方法、mGBA、ファイルの表示）は `gsmap/host.py` にあります。

Windows では同じ Linux 版エディターを WSL の中で動かします。WSL は alchemy を Windows でビルドする唯一の方法でもあります。
- `windows/Install-GS-Map-Editor.cmd`（リリースにはタグが埋め込まれた状態で同梱）は、必要なら WSL を有効にして Ubuntu をインストールし（管理者権限が必要で、再起動が必要になることもあります）、Ubuntu の中でそのタグの `windows/setup-in-wsl.sh` を実行し、`wsl.exe … gs-map-editor` へのスタートメニューとデスクトップのショートカットを追加します。
- エディターは WSL の localhost 転送を通じて Windows のブラウザーで開きます。プレイは `Program Files\mGBA` にある Windows 版 mGBA を、ゲームの `\\wsl.localhost\…` パスを渡して起動します。`/mnt/c` 上でのビルドは何倍も遅いため、ゲームは Ubuntu 自身のディスク上でビルドされます。
- Mac 以外のシステムでは、ページは ⌘ と ⌥ の代わりに Ctrl と Alt を表示します（`static/common.js` の `localWords`）。

`.github/workflows/linux.yml` は、プッシュのたびに GitHub の Ubuntu マシンでこれを確認します。`setup-in-wsl.sh` がエディターをインストールし、`tests/setup_flow.py` がインストールされたコマンドを通じて初回セットアップを最後まで進め、ビルドは `rom.sha1` と一致しなければならず、そのチェックアウトでラウンドトリップ・編集・配置のテストが実行されます。Windows 側（`.cmd`、WSL のインストール、ショートカット、Windows 版 mGBA）には自動テストがありません。Windows PC が必要です。

### リリース

リリースは GitHub が自社の Mac 上で `.github/workflows/release.yml` によってビルドします。Apple Silicon 用（`macos-15`）と Intel 用（`macos-15-intel`）のディスクイメージを 1 つずつ作ります。各ジョブはツールチェーンとアプリをビルドし、どちらもそのチップ向けであることを確認し、`packaging/smoke_test.py`（アプリが起動し、ツールを見つけ、固定先を表示する）を実行して `.dmg` を作ります。

1. `packaging/gsmapedit.spec` でバージョンを設定します（`CFBundleShortVersionString`）。
2. プレイヤーが読むリリースノートを `docs/releases/v<version>.md` に書きます。
3. コミットしてから `git tag v<version> && git push origin v<version>` を実行します。ワークフローは、片方のチップのジョブが失敗しても、両方のイメージ付きでプレリリースを公開します。

Actions ページの **Run workflow** は、リリースせずにイメージをビルドします。イメージには署名がありません。プレイヤーが Gatekeeper を通過する方法は README の「初めて開くとき」に書かれており、Developer ID が手に入れば `packaging/sign_and_notarize.py` が引き継ぎます。

## 各機能の仕組み

ローカルマップ、The Broken Seal、英語版。使い方は [README](../../README.ja.md) を参照してください。

- **表示:** 全 182 マップを、正しいタイルセットとプレースホルダー、レイヤーごとの表示切り替えと不透明度、コリジョンと高さのオーバーレイ付きで表示します。
- **ペイント:** ブロック、コリジョン、高さを塗れます。⌥-クリックでスポイト、元に戻す／やり直すにも対応します。編集していない部分は保存してもバイト単位で同一です。
- **スタンプ**（S）: 矩形をドラッグしてエリアをコピーし、クリックで貼り付けます。同じマップにも、同じブロックセットを使う別のマップ（Vale ↔ Debug · Sandbox）にも貼り付けられます。
  - コピーには 3 つのレイヤーすべてと、通行設定、高さが含まれます。
  - **オブジェクトのみ** は、下の地面ではなく木などのオブジェクトだけを貼り付けます（各レイヤーの背景ブロックとの色の比較による判定）。
  - 1 回の貼り付けは 1 回の元に戻す操作です。クリップボードはマップを切り替えてもページを再読み込みしても残ります。Esc でコピーに戻ります。
  - ブロックセットが異なるマップへの貼り付けは拒否されます。すべてのブロック番号が違うタイルを描いてしまうためです。
- **画像を読み込む…**（独自のタイルセットを持つマップ。現在は Debug · Sandbox）: PNG とレイヤーを選ぶとプレビューが表示され、**タイルセットに追加** を押します。新しいブロックはスタンプのクリップボードに入り、クリックで置ける状態になります。
  - インポーターは画像を 8×8 のタイルに切り分け、その色をマップの 14 個のパレット行のいずれかに合わせます（1 つの行ですべてが収まらない場合に限り、タイルごとに行を選びます）。インデックス 0 は透明です。
  - シートにすでにあるタイルは、反転したものも含めて再利用されます。
  - 新しいタイルはまず空きスペースに入ります。次に、マップが一度も置かないブロックだけが使うタイルの場所に入ります。それらのブロックは *引退*（パレットから隠され、スタンプが拒否する）し、alchemy の `games/tbs/src/mod/tilesets.json` に記録されます。
  - プレビューには、ゲームが描く色と、残りの空き容量が表示されます。
- **イベント**（E）: シーンで起きることすべてを、選んだストーリー段階について言葉で表示します。
  - **人物:** 「🗨 Garet: “Ever since the tremors started…”」、リードで読める心の声、独自の説明が付いたスクリプト（「出発前は村長について、戻った後は地震について尋ねる」）。
  - **場所:** 看板（A で読む）、足元メッセージ、調べる場所とそこで見つかるもの。
  - **出口エリア:** ドアとして働く矩形で、マップ上に描かれます。行き先を変えたり、削除したりできます。
  - 人物をクリックするとその人のイベントが表示され、**何か話させる**（またはストーリーの場面用のセリフを追加する）ことができます。任意の場所をクリックすると、**看板**、**足元メッセージ**、**人物** を追加できます。
  - **言葉を変更** は、ウィンドウのライブプレビュー付きのエディターを開きます。普通に入力し、空行で新しいウィンドウになります。**条件…** では「常に」、「<ストーリーフラグ> が立ってから」、「立っていない間だけ」を、フラグ名で設定します。
  - 新しいセリフは `en.po` のエディター専用ブロックに追加されます。ゲーム本来のセリフは書き換えられません。誰かのセリフを変えると、その人が新しいセリフを指すようになります。ゲームのフォントで描けない文字はビルドの前に拒否されます。
  - シーンが人物やイベントをほかのシーンと共有している場合（サンドボックスとデバッグハブがそうです）、パネルにそう表示されます。
- **ドア**（D）: すべてのドアがマップ上に行き先付きで表示されます（「→ Vale Home」）。どこにもつながらないドアは赤で表示されます。
  - ドアをクリックして **行き先を変更…** を押し、場所を選んでから、その場所のマップ上で到着地点をクリックします。
  - ほかの場所をクリックして **ここにドアを作る…** を押すと、ゲーム内のどこへでも行けるドアを追加できます。**ドアを削除** は、ドアのすべてのマスを地面に戻します。
  - シーンのスクリプトが開くドア（Vale のドアのほとんど）も、スクリプトがどの出口を求めているかを読み取って見つけます。行き先は変更でき、スクリプトはそのまま残ります。
  - ドアの変更は、出口とイベントのオーバーライドを通じて、そのシーンのすべてのストーリー段階に反映されます。シーンの `.c` ファイルには手を加えません。
- **宝箱**（K）: 空いている場所をクリックし、アイテム（アイコン付き）かコインの額を選んで **宝箱を追加** を押します。宝箱をクリックすると、中身を変えたり削除したりできます。
  - 1 回の操作で、宝箱に必要なものすべてを書き込みます。マーカー、そのマスのコリジョンコード、シーンのイベントテーブルにある `SEARCH(SEARCH_CHEST)` イベント（オーバーライドとして書くので、シーンの `.c` ファイルには手を加えません）、そして空いている宝箱用の範囲から取った新しい「開けた」フラグです。
  - コードは、マップのシーンのどのイベントテーブルも使っておらず、それらのテーブルを共有するどのマップのコリジョンにもないものを選びます。そのため、ほかの場所が調べられるようになることはありません。宝箱とストーンは 1 マップにつき最大 10 個です。
  - 宝箱は、マップの `map.s` の英語版の部分にある `treasure_spot` の行です。
- **宝箱とエナジーストーン:** ドラッグで移動します。マーカーの行と両方のマスのコリジョンコードが一緒に更新され、マーカーとコリジョンの規則を破る保存は拒否されます。
- **シーンテーブル:** マップを使う各シーンについて、テーブルを選びます。
  - 入口と NPC はマップ上に表示されます。人物を移動ツールでドラッグできます。
  - 出口はリスト（種類、行き先のシーン、入口、フラグ）として編集し、行き先の入口が存在するかを確認します。
- **つながり:** 任意の場所を中央に置き、そこへつながるすべての場所を左に、そこからつながるすべての場所を右に表示します（ドア、スクリプトのドア、シーンのイベントと、到着地点）。場所をクリックするとそこへ移動し、**開く** でエディター内のそのドアへジャンプします。
- **チェック:** すべてのマップを見て、変更によってゲーム内で起きる問題を平易な言葉で伝えます。それぞれに直し方と、その場所を開く **表示** ボタンが付きます。
  - どこにもつながらないドア、または存在しない到着地点につながるドア。
  - 開けられない宝箱、中身が設定されていない宝箱、一時フラグのせいで中身が復活する宝箱、「開けた」フラグを共有している宝箱。
  - 1 マップに 10 個を超える宝箱とストーン。存在しないブロックや引退したブロックを使うマス。
  - ゲームのソースと合わなくなったシーンテーブルの編集（alchemy の更新後）。
  - 元のゲームにもそれ自体のクセがあります（現在 115 件。例: 残されたドア 83 件）。各問題は変更前のゲームでも探され、そちらにあるものは表示を求めない限り隠されます。
  - **ビルド** はまずチェックを実行し、問題がある場合はビルドする前に確認します。
- **ワールドマップ**（場所の一覧の一番上）: 地上世界全体を、スクロールに応じて読み込みながら表示します。町とダンジョンのアイコンには行き先のラベルが付きます。
  - オーバーレイ: 通行設定（通れない地面は赤）とエンカウント地域。地域にはその中にある町の名前が付きます（「地域 1 (Vale, Lunpa…)」）。
  - **地面** ／ **オーバーレイ**: ブロックを塗ります（⌥-クリックで拾い、最近使ったブロックは手元に残ります）。**地域**: エンカウント地域を塗ります。変更は塗るたびに保存されます。元に戻すで最後のストロークを取り消し、やり直すで戻します。マスは `map/world/blocks.tsv` に書き込まれ、各ワードのほかのフィールドは保持されます。
  - **町**: アイコンをドラッグして移動します。その到着地点（町を出たときに現れる場所）も、そこにアイコンがあるすべてのストーリー段階で一緒に移動します。アイコンか青い足元の場所をクリックすると、行き先を変更できます。
  - 雪の北部は独自のグラフィックセットで描かれます。ポーズ画面の地図は別の絵で、編集には追従しません。
- **MOD を書き出し…:** MOD を小さな `.bps` パッチとして、プレイヤー向けの readme と一緒に `~/Documents/GSMapEditor/Exports/` に保存します。
  - パッチは変更前のゲームからあなたのビルドへの差分です。変更前のゲームは、MOD の出発点となるコミットから一度だけビルドされます。`git archive` で別のフォルダーに作るので、あなたのチェックアウトには手を加えません。alchemy の `rom.sha1` と照合されるので製品版カートリッジと同一であり、パッチは誰の吸い出しにも当てられます。
  - パッチは BPS 形式です（Rom Patcher JS、Floating IPS、エミュレーターのソフトパッチ）。移動したデータは新しいバイトではなくコピーになります。書き出したパッチはそれぞれ一度当ててみて、あなたのビルドを正確に再現することを確認します。
  - 書き出しはまずチェックを実行します。共有するのは変更点であり、ゲームそのものではありません。
- **パッチャー…:** MOD の `.bps`、`.ips`、`.ups` パッチを当て、ゲームを `~/Documents/GSMapEditor/Patched/` に保存します。**mGBA でプレイ** と **Finder で表示** が付きます。
  - パッチを当てる対象は、この Mac がソースからビルドした変更前のゲーム（ROM 不要）か、あなた自身の ROM ファイルです。あなたのファイルは alchemy の `rom.sha1` から名前が判別され（「Golden Sun (English)」）、変更前のゲームでない場合は警告が出ます。
  - BPS と UPS は違うゲームを拒否します。IPS は確認できないので、パッチャーがそう伝えます。
  - 書き出しでは古いパッチャー向けに `.ips` も書けます。IPS は移動したデータを記録できないためサイズが大きくなり（デバッグルームの MOD では 383 KB に対して 4.2 MB）、同じように確認されます。
- **▶ プレイ:** ボタン 1 つで、未保存の内容を保存し、チェックを実行し、ビルドして、mGBA でゲームを開きます。新しいゲームを、編集中の場所から始めます（ワールドマップのページからならワールドマップから）。開始位置は使い捨てのゲームのコピーに書き込まれ、書き出すものにはその痕跡が残りません。ビルドに失敗すると平易な説明が表示され、技術的な詳細は折りたたまれ、バグ報告用のコピーボタンが付きます。ビルドだけを行う操作は詳細設定の中にあります。
- **元に戻す / やり直す:** すべてに共通の 1 組のボタンです。元に戻すは、まず未保存のペイント（ページ自身のスタック）を取り消し、次に保存済みの操作を、どのツールやどの場所で行ったかに関係なく新しい順に取り消します。保存するとページのスタックは 1 つの保存済み操作になります。すべての書き込みは `server.py` の `writing(label, where)` を通ります。これは `gsmap/fsio.py` のトランザクションで、ファイルの古い内容を、何をどこで行ったかのラベル付きの履歴エントリーとして保持します（"adding a person"、マップ `051`）。`undo_last` はエントリーを元に戻し、置き換えた内容を `history/redo` に保持します。`redo_last` はその逆を行います。新しい操作は `history/redo` を消去します。どちらもジャーナルを通るので、途中でクラッシュしても次の起動時に完了します。それぞれ最新の 30 件が、サポートフォルダーの `history/` に保存されます。
- **人が立てる場所**（`gsmap/walk.py`）: alchemy のフィールドコードから得たゲームの歩行規則です。8 ピクセルの歩幅で 5 つのプローブがすべて空いている必要があり、上りは最大 8 ピクセル、下りは最大 12 ピクセル（`terrain.c`、`MapGrid_CheckCollision`）。高さは 16 個の地形関数と `terrain_tables.c` によって各マスの形状から求めます。段差、よじ登る場所、すき間があり、話しかけられるのは 32 ピクセル以内、上下 48 ピクセル以内です。滑る床は、スクリプトが滑らせる足元トリガーについて、`Imil_RunIceSlide` と同じようにたどります。パーティーはシーンのすべての到着地点から 8 ピクセルの格子上でたどられます。人物は 12 ピクセル以内をふさぎます（半径 8 を 2 つ、それぞれから 2 を引く）。`POST /api/map/<n>/walk` はすべてのマスを色分けします。`/walk/check` は、ある場所の問題、問題のない最も近い場所、そこまでの道を平らにする形状の編集（マップにすでにある平らな形状）を返します。未保存の形状と通行設定の編集も一緒に送られます。エナジーとストーリーイベントは考慮されず、確認対象以外の人物は障害物になりません。ゲームと照合した結果: Camelot が配置した人物の約 92% はこの規則で話しかけられ、残りはカットシーンの部屋とエナジーで開かれる場所です。
- **場所をリセット…:** 場所を元のゲームの状態に戻します（元に戻すであなたの版が戻ります）。ほかの場所が共有しているシーンテーブルはそのままにし、そう伝えます。
- **保存はすべてか無か:** 1 回の操作のファイルは一緒に書き込まれるか、まったく書き込まれないかのどちらかです。各ファイルは 1 ステップで置き換えられ、途中でエディターが止まった場合は次の起動時に取り消しを完了します。
- **名前:** 場所はゲーム内の名前で一覧表示されます（「Vale · Vale Home」）。
- **通行設定ブラシ:** 名前付きで色分けされています（床、壁、段差、登れる壁・はしご、ジャンプする隙間、ダメージ床、調べる場所など）。
- **ホバー:** マスが何をするかを表示します（「出口 → Vale」、「宝箱: Herb」、「スクリプト（おそらく … へのドア）」）。
- **NPC:** スプライトで描かれ、名前で一覧表示されます。
- **シーンテーブル:** わかりやすい名前で表示されます（「到着地点: 通常」、「人物: After Kalay」）。
- **詳細設定チェックボックス:** 生のコードを表示します。
- **リンク:** `?map=003&tool=points&kind=placements` で特定の場所を直接開けます。
- **アートやテキストを同梱しない:** アイテム・場所・キャラクター・スプライト・フラグの名前、アイテムのアイコン、スプライトのプレビューは、すべて実行時にプレイヤー自身の alchemy チェックアウトから読み込みます。`gsmap/data` にはエディター自身の調査結果だけが入っています。プレビューのフレーム、空いている宝箱フラグ、各通行設定コードの働きです。

**シーンの編集がゲームに届く仕組み:** alchemy のシーンファイルを書き換えず、1 つのフックを通じて届きます。`docs/SPEC.md` と alchemy の `games/tbs/src/mod/README.md` を参照してください。
- エディターは、編集したテーブルのコピーを alchemy の `games/tbs/src/mod/overrides.json` に保存し、そこから `mod.c` を生成します。
- `Scene_LoadOverlay`（`system/main_routine.c`）にある `MOD_SCENE_LOADED` は、エディターが初めてシーンの編集を書き込むときに素のチェックアウトに追加するもので、各シーン自身のテーブル選択ロジックを引き続き実行するラッパーに差し替えます。
- オーバーライドがなければ GSMOD は無効で、6 つの版すべてが引き続きバイト単位で同一にビルドされます。

次の段階は [`SPEC.md`](SPEC.md) のビルド計画にあります。

### alchemy への追従

エディターが alchemy の構成について知っていることは、すべて `gsmap/layout.py` にあります。テストに使ったコミットは `gsmap/setup.py` の `ALCHEMY_PIN` です。これを変えるときは README のバージョン行も更新してください。そうしないと安全テストが失敗します。新しいバージョンを試すには:

1. `python3 -m gsmap.preflight path/to/alchemy` は、何が合わなくなったかを平易な言葉で伝えます。これは毎回の起動時にも実行され、間違ったタイルでマップを描く代わりにそこで止まります。
2. ビルドしてから、`python3 tools/snapshot.py path/to/alchemy new.json` と `python3 tools/snapshot.py --compare old.json new.json` を実行すると、エディターが読み込む内容の違いがすべて表示されます。2 つのバージョンは同じゲームをビルドするので、結果は想定した箇所でだけ変わるはずです。
3. 下のテストを実行します。

既存のチェックアウトを新しい alchemy に手作業で移すのは、普通の git 操作です。新しいコミットをマージするかチェックアウトしてから、`git submodule update --init --recursive alchemy-gcc` を実行します。`alchemy-gcc` 3a12774（alchemy 2026-11-08）以降、agbcc は入れ子のサブモジュールではなく普通のファイルになったため、それより前のチェックアウトでは更新が「untracked working tree files would be overwritten」で止まります。`alchemy-gcc` の中で `git submodule deinit -f agbcc` を実行し、`agbcc` フォルダーと、alchemy-gcc の git フォルダーの下にある `.git/modules/agbcc` を削除してから、もう一度更新してください。最初のビルドの前に `out/*/deps.mk` と `out/*/objects.mk` を削除してください。2026-11-10 に alchemy-gcc の最新のコミットが書き直されて固定し直されたため、古いチェックアウトでの `git fetch` は「Errors during submodule fetch: alchemy-gcc」（「not our ref 8b1b6b4…」）で終わることがあります。それでもメインの fetch は成功しており、その後の `git submodule update` で新しい固定先がチェックアウトされます。セットアップの **ダウンロード** は常に新しくクローンするので、プレイヤーがこれに出会うことはありません。

保存されたシーンの編集には、それが作られたテーブルのフィンガープリントが付いています。上流で名前が変わったテーブルには追従します。元の内容が変わったテーブルへの編集は保持されますが、ゲームからは外され、チェックがそれを報告します。

### テスト

- `python3 tests/safety.py`: 決して起きてはならないこと。失敗やクラッシュで中途半端に保存されたファイルが残らないこと、元に戻すとやり直すが保存済みの操作を順にたどり、新しい変更がやり直しを消去すること、宝箱がそれぞれの部屋にとどまること、不正な値や悪意のあるパッチが拒否されること、名前が変わったり内容が変わったりしたテーブルが処理されること、未知の構成が推測されずに報告されること。
- `python3 tests/placement.py`: ゲームと照合した歩行規則。8 つの町に配置された人物に話しかけられ、出口に到達できること。また Imil で、氷、到達できない雪の場所（平らにする修正付き）、細い小道、玄関先、壁がそれぞれ警告されること。
- `python3 tests/edits.py`: 実際のマップのコピーにブロック・通行設定・高さの編集を保存し、それが読み戻せること、ほかに何も変わっていないことを確認します。
- `python3 tests/i18n.py`: コードが表示するすべてのメッセージがすべての言語に翻訳されていること、各翻訳が `{placeholders}`、HTML タグ、キー（⌘ ⇧ ⌥ ▶）を保っていること。
- `python3 tests/roundtrip.py`: すべてのマップグリッド、セル画像と形状のテーブル、宝箱リストを読み込んで保存し直します（デバッグルームの MOD 入りで 727 ファイル、素のチェックアウトで 721 ファイル）。すべてがバイト単位で同一でなければなりません。これにより、マップを保存しても編集した部分しか変わらないことが保証されます。

### 言語

エディター自身の言葉は翻訳され、ゲームは英語のままです。各メッセージは英語で書き、見つけられるように囲みます。Python では `tr("…")`（`gsmap/i18n.py`）、ページでは `T('…')`（`static/i18n.js`）です。最初の引数は常に 1 つの普通の文字列です。変わる部分は `{name}` プレースホルダーにし（`tr("Map {n} has {k} chests", n=n, k=k)`）、複数形は 2 つの完全なテンプレートにします。HTML ページ内のテキストや、スクリプトがページに入れるテキスト全体やタイトルは、メッセージと完全に一致するときにそのまま翻訳されます。`data-notr` 要素の中にあるもの（ゲームの名前やセリフ）はそのままにされます。ファイルに書き込むもの（mod.c、en.po、書き出した readme）や、コードが比較するものは翻訳しないでください。

`python3 tools/extract_strings.py` はすべてのメッセージを `static/i18n/<lang>.json`（英語 → 翻訳）に集め、新しいものを空で追加し、コードにもうないものを削除します。`--check` は、ずれているものや未翻訳のものがあると失敗します。🌐 メニューで選んだ言語はエディターの設定（`language`）に保存されます。選ばれるまでは、ブラウザーの優先言語で決まります。各リクエストのメッセージはそれを使い（両方のサーバーの `i18n.begin`）、ページは `/i18n-strings.js` からカタログを受け取ります。言語を追加するには、`gsmap/i18n.py` の `LANGS` に追加し、抽出ツールを実行して、新しいファイルを埋めてください。

README とこれらのドキュメントも翻訳されています。README の隣に `README.<lang>.md`、`DEVELOPING.md`・`PRODUCT.md`・`SPEC.md`・`research/` は `docs/<lang>/` にあります。`docs/upstream-issues.md`（alchemy の英語の課題管理用）、`docs/releases/`、`THIRD_PARTY_NOTICES.md` は英語のままです。英語のファイルが原本です。まず英語を変え、次に翻訳を変えてから、`python3 tools/doc_translations.py --stamp` を実行して、各翻訳がどの英語の文面に基づくかを記録してください。`--stamp` なしで実行すると、各翻訳のリンク・見出し・Web アドレス・`code` 部分を確認し、その後英語が変わった翻訳を一覧にします。通行設定ブラシの名前と説明（`gsmap/data/collision.json`）も抽出ツールが集めます。
